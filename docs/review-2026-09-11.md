# Review — 2026-09-11

Two passes over the tree: one as an engineer reading the code, one as someone
who would carry the pager for this inbox. The first found little; the second
found the real work.

Baseline: 618 tests pass. Nothing here is a fire.

---

## Part 1 — the code

The standard is high enough that most of this section is small. Worth saying
plainly, because it changes what the team should spend time on: **the code is
not the bottleneck. Coverage is.** Skip to Part 2 if you only read one.

### What is genuinely well done

Four things are better than typical and should survive any refactor:

- **The router's order id is only trusted when grounded.** `chat/actions.py`
  accepts `intent.order_group_id` only if it also appears in the message or the
  conversation, because a well-formed id can be fabricated — and one was, by
  `gemma3:latest`, which echoed the example id out of the routing prompt and
  read a production order nobody asked about. The failure is recorded in the
  comment next to the fix. That is normally lost within a month.
- **`decide_closure` lives in code, not in the model** (`models.py`), with the
  threshold justified by cost-of-error: marking a live ticket closed means
  nobody looks again. Both readers go through it, so they cannot disagree.
- **Checks report pass *and* fail** (`diagnose.py`). A reader sees what was
  ruled out, not only what fired. This is the difference between a diagnosis
  and an assertion.
- **Model calls run with `--tools ""` in an empty cwd.** Only the summarizer
  gets `Read`, confined to the attachment temp dir. The reasoning in
  `docs/phi.md` — that `--restricted` alone leaves the file tools pointed at a
  project directory containing `.secrets/` — is correct and easy to get wrong.

The XSS surface is also handled correctly, which matters because `index.html`
writes model output and email-derived strings through `innerHTML` in roughly
twenty-five places. `esc()` is `textContent`-based; `formatInline` escapes
*before* applying its markdown regexes; `linkify` matches only `https?://`, so
a `javascript:` href cannot be produced. Email bodies go through `esc()` in
`messageBlock`. Checked specifically, found nothing.

### Findings

**1. `days` and `limit` are unbounded from the router.** `intent.py:_pos_int`
has no ceiling, and `actions.run()` assigns both straight onto
`cfg.gmail.lookback_days` and `cfg.gmail.max_threads`. "Summarize the last two
years" is a well-formed route that fans out to a Gmail page walk and one model
call per thread, with no cap, no confirmation and no way to see the cost
coming. Given each summarize is a subprocess or an API call, this is the
cheapest way for a user to spend a lot by accident. Cap both, and say in the
reply that a cap was applied.

**2. The free-text filter matches JSON keys, not just values.**
`_apply_filters` tests `needle in json.dumps(row).lower()`, so the search runs
against key names as well as content. `search="other"` matches every row — via
the `other_ids` key inside `affected_entities` — and `other` is a configured
category, so this is reachable from a plausible question. `search="closed"`
matches everything for the same reason. `Store.query` has the analogous
problem with `payload LIKE '%…%'`, plus unescaped `%` and `_` acting as
wildcards. The result is silently wrong rather than empty, and the UI presents
it as a filter result. Match against a projection of the fields worth
searching.

**3. `actions.run()` mutates the Config it is handed.** `cfg.gmail.lookback_days
= intent.days` and friends. This is safe *today* only because `cfg()` reloads
from disk on every request. It is an invisible coupling: the first person who
caches the parsed config for performance introduces cross-request window
bleed, and nothing in the type signature warns them. `for_user()` already sets
the precedent for returning a derived copy.

**4. No CSP or security headers** on the two HTML responses. The escaping above
is correct, so this is defence in depth rather than a hole — but `chat/auth.py`
opens by arguing that the page renders untrusted email and therefore no
credential may be reachable from JavaScript. A CSP is the second half of that
argument and it is missing. Note that the inline `<script>` and `<style>`
blocks mean this needs a nonce or hashes, so it is not a one-liner.
`X-Content-Type-Options: nosniff` and `Referrer-Policy` are one-liners.

**5. `Sessions.purge()` runs exactly once**, when the store is first
constructed (`server.py:121`). A server that stays up never purges again.
Expired rows are still *rejected* at `get()`, so this is hygiene, not a
security gap — but `docs/service.md` leans on purge to keep the file bounded.

**6. `Sessions` shares one sqlite3 connection across threadpool threads.** Not
a bug today: `sqlite3.threadsafety == 3`, so SQLite serialises internally, and
every current write is effectively single-statement. It is fragile rather than
broken — `set_engine()` is already a two-statement sequence, and the first real
multi-statement transaction added here will interleave with another thread's
`commit()`. Worth a lock before Phase A puts two people on one replica, not
before.

**7. `fetch_json_report` GETs a URL from a payload with no host allowlist.**
`Authorization` is not at risk — httpx strips it across origins, and the call
deliberately uses a bare client anyway — so this is a narrow server-side-fetch
surface, not a credential leak. Worth a host check when this stops being a
laptop.

**8. Doc drift.** `docs/deploy.md` §5 says a second concurrent `/api/chat`
"gets a 409". It no longer does — `claim_turn` always succeeds and cancels the
previous turn, and the comment explaining why 409 was the wrong design is
better than the doc it contradicts. Fix the doc.

### One architectural note

`chat/actions.py:run()` is a ~400-line `if/elif` over `intent.action`, each
branch inlining its own gather, filter, stream and result assembly. It reads
fine at seven actions. It is also the file that fractures first: every new
action adds a branch that has to remember the config mutation, the streaming
protocol and the result shape. A dispatch table over handlers sharing one
`gather → filter → stream → result` spine would keep it flat. Not urgent —
flagged because Part 2 wants several new actions.

## Part 2 — as someone carrying the pager

Judged as an inbox-triage assistant, this is a strong Phase 1. Find, read,
summarize, categorize, and — for one narrow failure mode — actually diagnose
against production. That last part is rarer than it sounds.

Judged as **the tool an on-call rotation runs on**, there are real gaps. They
are not bugs; they are the difference between a reading tool and a working
tool.

### The one that matters most

**There is no category-to-runbook mapping at all.** This is sharper than
"coverage is thin", and it is worth stating precisely.

`diagnose.py` never reads `category`. Not once. Diagnosis is entered by an
**order group id** (`PO…`) scanned out of the thread, and it runs exactly two
checks — report name vs. record name, and report gender vs. record gender.
The UI's own tooltip is honest about their scope: *"Check the edit-patient
runbooks."* They fire on any order that reaches them, whatever the ticket was
categorised as.

Two consequences follow, and both are structural rather than incidental:

- **All thirteen categories have zero category-specific checks.** The roadmap
  asks for "a mapping from `category` to the checks worth running" and calls it
  "the whole game". That mapping does not exist yet in any form.
- **A thread with no `PO…` id cannot be diagnosed at all.** The Diagnose button
  is only rendered when `order_ids` is non-empty. Whole classes of ticket —
  consent and sharing questions, access problems, app crashes, deletion
  requests — have no entry point into the diagnostic flow regardless of what
  runbooks are written for them.

So the model classifies into thirteen buckets that the diagnostic layer cannot
see. The roadmap's own line — *"a category with no runbook is just a label"* —
is the accurate self-assessment, and today every category is a label.

**Do this first, and count before choosing.** The store already holds every
summary ever produced, with a category on each. Pick the top three by real
volume, and for each decide two things: what read-only checks would settle it,
and whether the thread even carries an identifier those checks could start
from. The second question is the one that is currently unasked — writing a
runbook for a category whose tickets carry no id buys nothing.

### The rest, roughly in order of what a rotation would miss

**No state — the bot cannot tell you what is still open.** `closed` is
re-inferred from the mail on every read. There is no acknowledged, in-progress,
assigned or escalated. Two engineers on the same rotation cannot see that one
has already picked a ticket up, and "what is still open from yesterday" does
not survive a re-read.

**No write path at all.** The scope is `gmail.readonly`. The bot cannot
acknowledge, reply, label, assign or snooze. Every loop closes in a human's
Gmail, unrecorded. `gmail.modify` plus a small label taxonomy is the smallest
useful write — and it gives the state problem above a home in the mailbox both
engineers already share, with no new datastore.

**No ageing or SLA view.** Severity exists; time-in-state does not. There is no
"P1 open for three days", no oldest-first, no breach list — `sort_by_severity`
is the only ordering. On a rotation, ageing is usually more actionable than
severity, and this one needs no new storage: `first_message_at` is already in
the store.

**Nothing proactive.** No poll, no schedule, no notification — no Slack,
PagerDuty or webhook anywhere in the tree. The bot speaks only when asked, in a
browser tab, on one person's laptop. A P0 arriving at 02:00 is found when
someone next opens the tab.

**No handover.** The single most-used on-call artifact is the shift handover:
what came in, what is open, what I did, what you should watch. Every input
exists — summaries, categories, diagnoses — and nothing assembles them.

**No dedup or recurrence.** No "this is the fifth report of this today", no
linking of related threads, no "someone asked about this order yesterday".
Grouping is per-window and thrown away. Recurrence detection is what turns
triage into a bug report, and it is the main thing that would let this tool
reduce ticket volume rather than just describe it.

**No memory of resolutions.** Nothing records what actually fixed a ticket, so
the same diagnosis is re-derived from scratch every time and the bot can never
say "last time this was X". The store keeps summaries; it never keeps outcomes.

**No metrics.** `/api/context` gives counts by severity and category over the
cache. There is no volume over time, no MTTR, no category trend. This also
blocks the roadmap's own plan: Phase 2 says to run diagnose-only for a few
weeks and compare against tickets a human resolved, but nothing stores the
human outcome, so there is nothing to compare against. **Phase 3 cannot be
justified until this exists.**

**Single-user-shaped.** Everyone runs their own copy, own cache, own model
spend. Two on-call engineers get different answers to the same question
depending on cache state, and neither can see the other's work.
`docs/service.md` is honest about this being a deliberate Phase 1 choice — it
is still the thing that stops it being a team tool.

**No audit log, no retention.** Both already documented as overdue —
`docs/deploy.md` §2 and `docs/service.md` Phase A. Confirmed still absent:
nothing in `src/` writes an access record, and nothing deletes a summary.
`.data/users/*.sqlite3` holds patient-derived summaries forever. For PHI, "who
saw this patient's summary" is the first question an audit asks.

## Suggested sequencing

**Near term — better tool for one person, no new infrastructure**

1. Count categories in the existing store. For the top three, define the
   read-only checks *and* confirm their tickets carry an identifier to start
   from. Then add the `category` → runbook mapping `diagnose.py` currently
   lacks entirely.
2. Ageing / oldest-first view and an "open from earlier" list, derived from
   `first_message_at`.
3. Cap `days` and `limit`. Fix the search filter. Update `deploy.md` §5.
4. `nosniff` + `Referrer-Policy` now; CSP with hashes when someone has an hour.

**Medium — makes it a team tool**

5. Read audit log. Required before anything is shared, and cheapest to add now
   while there is one writer.
6. Retention policy and a delete path.
7. `gmail.modify` and a label taxonomy for state, so state lives in the shared
   mailbox.
8. Shift handover generator.
9. Recurrence and dedup keyed on `affected_entities` plus category.

**Longer — Phase A/B from `service.md`, unchanged**

10. One shared replica, Postgres, work queue, TLS, an audience narrower than
    the domain.
11. Outcome capture, so Phase 3 has an accuracy baseline to point at.

The ordering is deliberate: 1 and 2 change what on-call can do this week; 5 and
6 are the ones that get expensive to retrofit; 11 is the gate on everything in
Phase 3.
